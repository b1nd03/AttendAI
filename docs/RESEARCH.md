# Research, decisions, and camera calibration

Reviewed 5 November 2026. The user's original research plan motivates pretrained embeddings, a growing gallery, strict unknown rejection, quality/liveness gates, and reversible updates. The implementation adds the continuous multi-camera capture and human naming workflow clarified later.

See the [5–15 m model comparison and field-test plan](LONG_RANGE_RESEARCH.md) for newer research, camera geometry and the six-feed upgrade path.

## Live camera performance

The performance update follows [Frigate's GitHub live-view design](https://github.com/blakeblackshear/frigate/blob/dev/docs/docs/configuration/live.md) and [camera setup guidance](https://docs.frigate.video/frigate/camera_setup/), which separate smooth viewing from lower-rate detection. AttendAI applies this design to its existing local capture. Browser webcam video plays from its media stream while the server analyzes up to five recent frames per second. Direct camera previews read the newest frame without waiting on detection. The inspection view keeps boxes aligned to the exact analyzed frame.

[OpenCV Zoo's YuNet implementation](https://raw.githubusercontent.com/opencv/opencv_zoo/main/models/face_detection_yunet/README.md) documents the detector's sensitivity to the size of faces in its input. Tests compared several resolutions at the existing confidence threshold. A 640-pixel long edge missed the two-face fixture, while 832 detected both faces in the original and 1280×720 test variants. The detector uses that measured starting point and maps its landmarks back to the source pixels for alignment, embeddings, and liveness. Model weights, consent, identity thresholds, and the requirement for distinct observations remain in the existing pipeline. Evaluate distance and pose with your cameras because detector input size can affect recall.

The web update uses route-level imports and compresses script and stylesheet responses. Only Vite's fingerprinted static assets are cached for reuse. Workspace responses and camera images retain their private, nonpersistent handling. [HTTP cache directives](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

## Face quality across camera resolutions

The previous focus check used the variance of a Laplacian over the raw detected box. The result depended on the crop's pixel scale and included detail outside the central face. The reported webcam example reproduced the problem. YuNet detected the face, but the raw detail score was about 17 against a cutoff of 45. The same screenshot passed after alignment with a score of about 68. The screenshot resized to the old 960-pixel upload limit passed at about 62. A heavily blurred version still produced a detection and failed the detail check. The example was processed locally for diagnosis.

The new check uses the central region of the 112×112 SFace alignment and lightly filters sensor and compression noise before measuring detail. Size, crop boundaries, exposure, and detail have separate feedback. Browser sharing asks for a 1080p source and sends up to 1280 pixels on the long edge for analysis. The browser can negotiate a different source size, so the camera card reports the actual source and analysis sizes. [NIST FATE quality evaluations](https://pages.nist.gov/frvt/html/frvt_quality.html) · [OpenCV SFace alignment and matching](https://docs.opencv.org/4.x/d0/dd4/tutorial_dnn_face.html) · [Browser track settings](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/getSettings)

Published learned approaches include [AdaFace](https://openaccess.thecvf.com/content/CVPR2022/html/Kim_AdaFace_Quality_Adaptive_Margin_for_Face_Recognition_CVPR_2022_paper.html), which trains an embedding model with a quality-adaptive margin, and [SER-FIQ](https://openaccess.thecvf.com/content_CVPR_2020/html/Terhorst_SER-FIQ_Unsupervised_Estimation_of_Face_Image_Quality_Based_on_Stochastic_CVPR_2020_paper.html), which estimates quality from the stability of repeated stochastic embeddings. The reproduced rejection happened before embedding, so the release fixes that gate and keeps the existing pretrained SFace gallery compatible. A test fixture's original and mildly blurred images had a cosine similarity of 0.94 after the change. This is a regression check on one public image. A model replacement would require separately calibrated thresholds, held-out comparisons on the target cameras, and a gallery migration.

## Why this tracker instead of a forced classifier

Several people may be visible in a frame, so the kiosk's single-face consensus was replaced in the primary monitoring path. Each face passes independently through quality, embedding, conservative spatial/appearance association, and temporal voting. A visually incompatible observation cannot inherit an existing name simply by occupying the same box. Unknowns are grouped for human labeling, not force-assigned to the closest name.

This implementation is a conservative multi-face tracker, not a claim of ByteTrack/DeepSORT equivalence. A full-body detector/tracker could maintain trajectories when faces turn away, but would need additional models, scene tests, identity handoff validation, and licensing decisions. The current system deliberately does not assert who an invisible or back-facing person is.

## Model comparison and recognition under brief interruptions

[Neural Aggregation Networks for Video Face Recognition](https://openaccess.thecvf.com/content_cvpr_2017/html/Yang_Neural_Aggregation_Network_CVPR_2017_paper.html) motivates using evidence from a video track and discounting uninformative frames. AttendAI uses a bounded voting rule with its existing embeddings. An identity can retain evidence across up to two uncertain observations within the required vote window. Those observations add no identity votes, and a competing identity or quality failure clears prior support. Liveness must still pass throughout the window, including the uncertain observations. In a regression track with five matching observations separated by two uncertain ones, the prior rule never reached five consecutive matches. The new rule confirms the match only with sufficient liveness and still rejects evidence split across competing identities.

[NIST's 1:N evaluations](https://pages.nist.gov/frvt/html/frvt1N.html) report missed identifications at a controlled false-positive identification rate, which is the target for a future in-room model comparison. [NIST's presentation-attack evaluation](https://pages.nist.gov/frvt/html/frvt_pad.html) treats liveness as a separate problem. A more discriminative recognizer cannot validate liveness by itself.

Four model variants were run on this Windows CPU with OpenCV 4.12. The test used three aligned faces from existing or public software fixtures, then made 12 same-image probes with low illumination, 45-pixel downsampling, blur, and JPEG compression. Each probe was compared with all three clean references. Median and p95 times use 36 warmed embedding calls per model. Times exclude detection, tracking, and liveness. Weights were checksum-verified. AuraFace was pinned to `af6d057c9b0ec4071d4c49c80e3539258798b609`. [OpenCV Zoo SFace variants](https://raw.githubusercontent.com/opencv/opencv_zoo/main/models/face_recognition_sface/README.md) · [AuraFace model card](https://huggingface.co/fal/AuraFace-v1) · [Astronaut fixture](https://scikit-image.org/docs/stable/api/skimage.data.html#skimage.data.astronaut) · [Matplotlib fixture](https://github.com/matplotlib/matplotlib/blob/v3.10.0/lib/matplotlib/mpl-data/sample_data/grace_hopper.jpg)

| Model | Embedding median / p95 | Lowest same-face cosine | Highest other-face cosine |
|---|---:|---:|---:|
| SFace FP32 | 10.95 / 14.29 ms | 0.712 | 0.157 |
| SFace INT8 | 22.30 / 23.71 ms | 0.703 | 0.147 |
| SFace block INT8 | 10.36 / 14.79 ms | 0.714 | 0.156 |
| AuraFace R100 | 134.75 / 173.80 ms | 0.501 | 0.244 |

The smoke data uses synthetic degradations of only three source images and does not estimate real-world miss or false-match rates. This test showed similar results for both fast SFace variants and substantially higher CPU time for AuraFace. SFace FP32 stays active with the existing enrollment templates. AdaFace R18 remains a candidate for a separate test on independent camera footage, with its own enrollment templates and thresholds. [AdaFace paper](https://arxiv.org/abs/2204.00964) · [Released checkpoints](https://github.com/mk-minchul/AdaFace#pretrained-models)

Matching now indexes existing SFace vectors once and scores them with NumPy. The best-two similarity and runner-up margin rules retain the same definitions. In a separate 50-query test against 1,000 synthetic people with five templates each, median gallery search time went from 11.923 ms to 0.199 ms. This measures only matching. Camera inference time remains separate.

## People and faces at room distance

Wide-angle footage can contain a clear body and very little face detail. Using Axis's 16 cm illustrative face width, a 3840-pixel camera at 10 m with a 90° horizontal field of view yields approximately 31 pixels across the face. A 35° view at the same distance yields approximately 97 pixels. This is a geometric estimate for a frontal subject near the image center. Check actual source pixels at the intended recognition point. AttendAI's default quality floor is 90 pixels across the smaller dimension of the detected face, with separate alignment, matching, and liveness gates. [Axis pixel-density guidance](https://whitepapers.axis.com/en-us/pixel-density-based-on-iec-62676-4-2014)

Room-distance mode uses OpenCV Zoo's pretrained 3.8 MB NanoDet-M-Plus checkpoint for person proposals. Wide streams use overlapping views to expose more pixels per person to the body model. This follows the small-object rationale in SAHI without requiring the SAHI runtime. Sparse Lucas–Kanade flow follows anonymous regions between body detections. YuNet then checks each head region and a separate full-scene overview. Head crops are mapped back to the original stream for face size, alignment, SFace, and MiniFASNet. The app can report a person while withholding an identity when the face is turned away, obscured, or too small. [OpenCV Zoo NanoDet](https://github.com/opencv/opencv_zoo/tree/main/models/object_detection_nanodet) · [SAHI paper](https://arxiv.org/abs/2202.06934) · [OpenCV optical flow](https://docs.opencv.org/4.x/d4/dee/tutorial_optical_flow.html)

In a controlled 3840×2160 composite using a public object-detector fixture, standard mode found no faces. Room-distance mode found three bodies and two faces approximately 39 pixels across, which remained below the attendance quality floor. The three-view body scan took about 162 ms median over ten warmed runs. The face search with existing proposals took about 46 ms median over four runs. Body scans are spaced about a second apart on a wide 4K stream, with motion updates on analyzed frames in between. A second composite confirmed that a usable face with over 90 source pixels passed the new crop path while standard resizing discarded it. The composite tests do not establish the mounting distance or liveness performance of a work camera. [Public detector fixture](https://github.com/ultralytics/ultralytics/blob/main/ultralytics/assets/bus.jpg)

## Tilted faces and camera edges

A reported webcam preview showed zero detections for a tilted face near the bottom edge. A padded, rotated search view recovered the face above YuNet's regular confidence threshold. Roughly 10% of the detected rectangle fell beyond the actual camera image. Live monitoring now checks a bounded sequence of orientations after an empty regular scan and reuses a successful angle. It maps detections back to the camera frame, measures visible coverage, and uses real source pixels for embeddings and liveness. A clipped detection shows framing guidance. Fully visible tilted test faces can continue to matching. Padding serves the detector and supplies no pixels for matching or liveness. [Rotation-invariant face detection research](https://openaccess.thecvf.com/content_cvpr_2018/papers/Shi_Real-Time_Rotation-Invariant_Face_CVPR_2018_paper.pdf)

The secondary detector uses the 7.5 MB CenterFace ONNX model pinned to upstream commit `b82ec0c4844e89fd5a0305986aed9bdf33c72585`. CenterFace has a separate detector and five-landmark head. It found all three versions of a public fixture composited into a 1280×720 frame at 0°, 35°, and 55°, where the regular YuNet overview missed them. On this CPU, a secondary empty-frame pass including preprocessing took about 68 ms median in a ten-run probe. The scheduler attempts one recovery view at a time after a miss. In the original webcam example, CenterFace plus rotation reported the clipped edge. On the fully visible 55° test case, the recovered SFace embedding scored about 0.90 cosine against the clean fixture. These are regression probes. The system still requires valid source coverage, face quality, matching consensus, and liveness for attendance. [CenterFace model and code](https://github.com/Star-Clouds/CenterFace) · [CenterFace paper](https://onlinelibrary.wiley.com/doi/10.1155/2020/7845384)

## Two-model recognition and rollout

The second pilot used 24 identities from the checksum-verified LFW funneled archive. Six independently photographed images per identity were accepted by the same alignment stage. Sixteen identities supplied three enrollment images each and 48 different probes. Eight held-out identities supplied 24 unenrolled probes. Probes were dimmed and downsampled to 48 or 68 pixels after alignment. This measures embedding behavior under controlled degradation, with overlapping training identities possible and no camera tracking or liveness in the benchmark. [LFW dataset reference](https://scikit-learn.org/stable/modules/generated/sklearn.datasets.fetch_lfw_people.html)

| Model | CPU median per embedding | Correct top rank before thresholds | 10th percentile genuine score | Highest unenrolled score |
|---|---:|---:|---:|---:|
| SFace | 17.3 ms | 48/48 | 0.480 | 0.361 |
| AuraFace R100 | 156.5 ms | 48/48 | 0.438 | 0.272 |
| AdaFace IR101 WebFace12M ONNX | 135.8 ms | 48/48 | 0.586 | 0.202 |

AdaFace separated the known and unenrolled probes best among the tested standalone models. The ONNX export was verified against its release hash. The original checkpoint author directs users to follow the dataset license. Workplace deployment rights for that checkpoint were not verified, so it was evaluated separately. The CVLFace authors also report stronger TinyFace results with ViT KP-RPE, a larger research candidate with separate deployment and latency requirements. AuraFace is published for commercial use and is deployed as a secondary check. [AdaFace checkpoint terms](https://huggingface.co/minchul/cvlface_adaface_ir101_webface12m) · [ONNX export](https://github.com/yakhyo/adaface-onnx) · [CVLFace results](https://github.com/mk-minchul/CVLface) · [AuraFace model card](https://huggingface.co/fal/AuraFace-v1)

Requiring the second model for accepted SFace matches produced more misses. The deployed policy preserves accepted SFace matches and considers only near misses with a clear leading candidate. AuraFace searches the same roster independently and must agree on that candidate at a separate 0.46 score and 0.12 margin. This pilot setting recovered two of six baseline misses, yielding 44/48 correct matches versus 42/48. Both runs accepted zero of the 24 unenrolled probes. The pilot helped select the setting and is too small to establish a production false-match rate. Existing distinct-frame consensus and liveness still apply, and AuraFace-assisted votes cannot drive automatic template learning.

Each model uses its own encrypted templates. An incomplete roster remains on SFace so the second search cannot hide a competing identity. New enrollments and newly collected camera samples generate both models' templates after operator verification. Legacy profiles can refresh their faces without changing their ID or attendance history. When saving unknown faces is enabled, encrypted alignment crops follow the same expiration and deletion lifecycle as the corresponding samples. [NIST 1:N identification methodology](https://pages.nist.gov/frvt/html/frvt1N.html)

## Calibration procedure for your cameras

1. Place cameras where faces remain large and frontal enough. Choose a useful substream and frame rate before raising inference resolution blindly. Check actual preview age and analysis latency under all connected sources.
2. Enroll or name a small consenting test group. Keep verified enrollment captures separate from evaluation tracks, using different days and approaches. Do not tune and report on the same tracks.
3. Collect held-out genuine approaches and non-enrolled/incorrect-identity approaches. For an open-set system, nonmate scores should be the strongest incorrect gallery result at the deployed gallery size, not convenient random pair scores. Keep per-camera results and inspect ambiguous runner-up margins.
4. Evaluate temporal accepted tracks, not just individual frames. Record false accepted identities, missed known arrivals, ambiguous/rejected tracks, time to confirmation, and duplicate attendance. Test two simultaneous faces and crossing paths.
5. Run printed-photo, phone-screen, and recorded-video presentations on each camera. Test the actual lighting and camera pose. Independently measure liveness false acceptance/rejection; a similarity threshold does not evaluate spoof resistance.
6. Enable shadow operation first: cameras in sightings-only mode, manually verify outcomes, and adjust rules. Threshold changes remain explicit operator actions. Promote to automatic attendance only after held-out results support the selected operating point.
7. Enable gallery updates for a pilot group. Compare a frozen-anchor baseline with adaptive galleries across later held-out days. Keep rollback evidence and examine each update. Re-evaluate after camera moves, model changes, and substantial gallery growth.

Use the included score evaluator for an **initial score-only analysis**, not an end-to-end certification:

```powershell
.\.venv\Scripts\python.exe scripts\evaluate_thresholds.py path\to\verified-scores.csv --target-far 0.001 --output threshold-report.json
```

Input columns: `label,score`, where `label` is `genuine` or `impostor`; scores must use the application's actual aggregate similarity convention. The tool reports FAR/FRR across thresholds and a Wilson upper bound. It refuses to recommend a threshold when sample size cannot support the requested FAR bound. Correlated frames are not independent trials; use held-out track/subject data, and interpret intervals accordingly. Margin, quality, liveness, tracking and attendance logic require their separate end-to-end validation.

## Reproducibility

`scripts/download_models.py` pins OpenCV Zoo commit `48b10fa505aeb51fbd127fc60a5c660040e823b7` and MiniFASNet commit `b6d5f04ad78778917853b25c778acef6d5626d15`. All four weight files have explicit SHA-256 checks; the manifest records them. MiniFASNet network/crop definitions are vendored unmodified with the upstream license. Dependencies are listed in `package-lock.json`, `requirements.txt`, and the installed-environment lock snapshot.

Unit tests inject known embeddings to verify decisions and use real models for one/two-face smoke inputs. Browser tests exercise the local application against isolated data. None of those tests substitute for physical camera and population testing. No private training dataset or real camera credentials are bundled.
