# AttendAI code audit and model research

6 November 2026. The review covered the local browser, IP and USB camera paths, frame scheduling, face detection and matching, liveness, naming, attendance, SQLite writes, and the operator's Live Monitor.

## Findings addressed

| Priority | Finding | Implemented change |
|---|---|---|
| High | An entrance camera could discard a second check-in after an enter, exit, and re-entry on the same uninterrupted track. The event key was tied to direction for the life of the track. | Deduplicate within each physical crossing. A conflicting identity or extended loss of usable face evidence invalidates the previous crossing context. |
| High | A database error could mark a crossing or review group as recorded in memory before the transaction committed, preventing a retry. | Publish in-memory event and review markers after commit. A temporary write failure can retry while the crossing is still fresh. |
| High | This Windows runtime ships SQLite 3.49.1, an affected version for the documented WAL-reset race. Multiple application threads can open the same database. | Use rollback journaling on affected versions and retain WAL on fixed versions. Ordinary retention polls stay read-only when nothing has expired. [SQLite WAL-reset notice](https://www.sqlite.org/wal.html#the_wal_reset_bug) |
| Medium | A face could pass image-quality checks under old settings, then be scored after the settings or gallery changed. | Discard that in-flight face result before identity or attendance writes. |
| Medium | A smooth raw preview could display a live badge after analysis stalled. The UI also hid whether all profiles had the stronger model's templates. | Show camera and analysis status separately. The readiness strip shows live and analyzed sources, enrolled people, and two-model coverage. |
| Medium | Camera polling could erase a sightings error, and a failed review request could look like an empty queue. | Give camera status, recent sightings, and the naming queue their own loading, failure, and retry states. |

## Model assessment

**ViT KP-RPE with WebFace12M is the stronger pretrained research candidate to evaluate next.** The authors report 76.10% rank-1 on TinyFace, compared with 72.42% for their AdaFace IR101 WebFace12M. Their IJB-C figures are 97.82% and 97.72% at 0.01% false acceptance. These results come from the authors' evaluation and do not rank either model on AttendAI's cameras. The checkpoint expects aligned facial keypoints and asks users to follow the training dataset's terms. Workplace deployment rights and local throughput have yet to be established. [CVLFace performance board](https://github.com/mk-minchul/CVLface#face-recognition-performance-board) · [Pretrained checkpoint](https://huggingface.co/minchul/cvlface_adaface_vit_base_kprpe_webface12m) · [KP-RPE paper](https://arxiv.org/abs/2403.14852)

**Current workplace pipeline.** YuNet and CenterFace handle face detection, NanoDet proposes body regions in room-distance mode, SFace does the regular identity search, and AuraFace checks selected near misses once every profile has compatible templates. The previous degraded-photo pilot recovered 44/48 enrolled probes with two models, versus 42/48 with SFace, and accepted zero of 24 unenrolled probes. AdaFace IR101 had the strongest score separation among the standalone models tested locally. These were image-level pilot results. A future model needs a separate versioned gallery and calibrated thresholds. [Local benchmark method](RESEARCH.md#two-model-recognition-and-rollout) · [AuraFace model card](https://huggingface.co/fal/AuraFace-v1)

**Commercial evaluation.** If an enterprise SDK is an option, use NIST's one-to-many webcam and profile columns to shortlist vendors and request an on-device test. Compare missed identities at the same false-positive identification rate and verify the SDK's availability and integration terms. NIST FIVE is the closer test design for distant, compressed, multi-person video. [NIST 1:N identification](https://pages.nist.gov/frvt/html/frvt1N.html) · [NIST Face in Video Evaluation](https://www.nist.gov/programs-projects/face-video-evaluation-five)

## Next validation in order of impact

1. **Measure the camera image first.** Check source resolution, face pixels at the actual doorway, head angle, and light at 5 and 10 m. A 4K stream can still yield a very small face with a wide lens. Use a high-resolution detection feed where distant faces need it and measure each stream under actual load. [Axis pixel density](https://whitepapers.axis.com/en-us/pixel-density-based-on-iec-62676-4-2014) · [NIST image quality](https://pages.nist.gov/frvt/html/frvt_quality.html)
2. **Run a sightings-only pilot.** Collect separate, consented enrollment, calibration, and held-out approach clips from the target cameras. Include enrolled and unenrolled people, crossing paths, backlighting, blur, and different days. Record one outcome per approach, including wrong identity, missed identity, no usable face, direction error, and duplicate attendance. Compare model versions at the same false-positive identification target. Count independent approaches and report uncertainty. [NIST FIVE test design](https://pages.nist.gov/frvt/html/frte_five.html)
3. **Test liveness independently.** Include live approaches and authorized print and screen presentations. Report legitimate rejections and accepted attacks separately by camera and presentation type. Keep operator review or sightings-only for cameras where the result is insufficient for automatic attendance. [NIST passive liveness evaluation](https://www.nist.gov/publications/face-analysis-technology-evaluation-fate-part-10-performance-passive-software-based)
4. **Profile concurrent sources before changing inference engines.** The current shared scheduler bounds the queue but serializes analysis. AuraFace can also extend the time spent holding the attendance mutation lock. Measure per-camera p50/p95 capture-to-decision latency, analyzed FPS, and dropped frames at the planned camera count. If the shared path is the bottleneck, move expensive inference outside the write lock, revalidate the gallery/settings revision before commit, and benchmark a compatible accelerated runtime against the current CPU build. [ONNX Runtime performance guide](https://onnxruntime.ai/docs/performance/tune-performance/)
5. **Use server-connected sources for unattended work.** Browser sharing depends on a live tab and session. Background browser throttling and laptop sleep can interrupt frame delivery. The monitoring checklist should cover a source outage, reconnect, a failed name queue, and a later verified return to normal. [Browser background behavior](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

The automated suite exercises software behavior using controlled frames and isolated workspaces. Actual workplace accuracy, liveness, and sustained multi-camera throughput require the pilot above.
